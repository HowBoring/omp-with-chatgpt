### 为什么“原样”不能直接用于 OMP

项目本身分成两层：

```text
ChatGPT Web
   │
   │ MCP：读取 workspace
   ▼
C2C Bridge
   │
   ▼
Local Workspace
   ▲
   │ edit / shell / git / test
   │
Codex Harness
```

官方架构明确把 C2C Bridge 定义为 **read-only MCP Server + OAuth + Pairing + Tunnel + workspace access**，而实际修改代码、运行命令、测试等由 Codex Harness 完成。

其中 **C2C Bridge 本身并没有明显依赖 Codex runtime**。它只是：

- 提供 `workspace_info`
- `read_file`
- `search_workspace`
- `git_status`
- `git_diff`
- `test_status`
- `execution_summary`
- `execution_output`
- 等只读 MCP 能力

而 ChatGPT 通过这个 MCP 自己读取代码。README 也明确把它描述成 **“MCP data plane + coding harness control plane”**。

真正的问题在 `skill/SKILL.md`。

```text
Official skill: control-in-app-browser

setupBrowserRuntime()
const iab = await agent.browsers.get("iab")
```

```text
tab.markHandoff()
tab.markDeliverable()
iab.capabilities.get("visibility")
```

等机制。

这些不是通用 Agent Skills API，而是 **Codex 自己的 in-app browser runtime**。

OMP 的浏览器接口完全不同。目前 OMP 使用：

```js
const tab = await browser.open({
  name: "main",
  url: "https://chatgpt.com"
});

const observation = await tab.observe();
await tab.id(...).click();

await tab.goto(...);
```

并支持 headless / spawned / CDP / relay 等 browser backend。

所以当前 Skill 如果直接让 OMP 执行，到 Browser setup 那一步基本就会失败。

# 3. 为什么应该是 Extension + Skill，而不是二选一

这是二次分析里最关键的结论。

OMP 官方现在明确把 **Extension** 定义成首选 runtime 扩展机制。它能同时：

- `pi.on(...)`
- `registerTool(...)`
- `registerCommand(...)`
- 拦截 `tool_call`
- 监听 `session_start`
- 监听 `before_agent_start`
- 监听 `session_stop`
- 注入消息
- 持久化 extension state

而且官方明确说：

> Extensions are a strict superset of hooks. New authoring should use ExtensionAPI.



因此状态机应该由 Extension 控制。

但 **ChatGPT Web browser interaction 不应该塞进 Extension**。

因为 OMP 的 `browser` 目前是 Eval prelude，而不是普通 Extension Tool；标准用法是模型通过：

```js
browser.open(...)
tab.goto(...)
tab.observe()
tab.run(...)
```

访问。

如果为了让 Extension 自己操作浏览器，而去 import：

```text
tools/browser/tab-supervisor
tools/browser/registry
...
```

这些 OMP 内部实现，adapter 会严重绑定 OMP internal API。

所以正确分工是：

```text
Extension
   │
   │ "当前需要 GPT_PLAN"
   │ "请执行 C2C browser exchange"
   ▼
LLM
   │
   │ load skill://c2c
   ▼
Skill
   │
   ▼
browser.open / tab.run
```

也就是：

> **Extension 管“何时必须做”；Skill 管“具体怎么做”。**

这比上一轮“Skill 自己管全部流程”明显更稳。

```text

    ↓
1 ChatGPT chat
```

更好的关系是：

```text
1 workspace
    ↓
1 ChatGPT Project
1 MCP connector
    ↓
N OMP sessions
    ↓
N ChatGPT chats
```

例如：

```text
Kms workspace
│
├── MCP connector: Kms
├── ChatGPT Project: Kms
│
├── OMP session A
│      └── ChatGPT chat A
│
├── OMP session B
│      └── ChatGPT chat B
│
└── OMP session C
       └── ChatGPT chat C
```

这实际上正好利用了 C2C 当前已经支持的 `project` conversation mode：一个 workspace 一个 Project，新 coding-agent conversation 可以在 Project 内开新 chat。

这样并发 session 不会：

```text

B: INIT task-B
A: REVIEW task-A
B: PLAN task-B
```

全部混在同一个 ChatGPT conversation 中。

# 7. OMP branching 也因此有一个明确语义

这是 OMP 适配中特别值得处理的点。

假设：

```text
OMP Session
     A
     │
     B
     │
     C
     │
     D
```

用户从 B branch：

```text
       C -- D
      /
A -- B
      \
       C' -- D'
```

OMP session transcript 本身可以正确 rewind 到 B。

但 ChatGPT chat **不能 rewind**：

```text
ChatGPT
A → B → C → D
```

如果继续使用旧 chat，GPT 已经知道 C/D，而新的 OMP branch 实际上位于 B。

所以最合理的 branch policy 是：

```text
OMP session_branch
       ↓
fork C2C conversation
       ↓
new ChatGPT chat
       ↓
HANDOFF(branch-local state)
```

这比简单保存一个 workspace-global chat URL可靠很多。

```text
mutating bash
```

OMP 官方允许 `tool_call` handler 在执行前 **block 或修改 tool input**。

所以不会再依赖一句 prompt：

> “请不要在 PLAN 之前修改文件。”

而是：

```text
GPT_PLAN not received
        ↓
edit(...)
        ↓
BLOCKED BY C2C EXTENSION
```

这是真正意义上的 protocol enforcement。

---

# 9. Review gate 也应该由 Extension 管

执行结束后：

```text
PLAN_RECEIVED
     ↓
implementation
     ↓
tests
     ↓
EXECUTED
     ↓
GPT_REVIEW
```

只有 GPT 返回：

```text
DONE
```

主 Agent 才允许正常结束。

OMP 的 `session_stop` 正好可以做最终 completion guard。官方甚至明确提供：

```text
session_stop
```

来阻止或要求 agent 在结束前继续工作。

不过我不建议让 `session_stop` 成为整个循环的主驱动器，因为它的 advisory continuation 有数量限制。

更合理的是：

```text
正常 agent loop
       +
tool_call state gate
       +
session_stop final guard
```

也就是：

```text
tool_call = execution safety gate

session_stop = completion safety gate
```

而不是拿 `session_stop` 做 workflow engine。

---

# 10. Browser 方案也需要调整

上一轮我只是说：

```js
browser.open(...)
```

但二次分析后可以做得更准确。

OMP 当前正常 CLI 运行时，会为一个 project 启动 **project-shared automation Chromium**：

```text
project
   ↓
shared Chromium
   ↓
session A tab
session B tab
subagent tab
```

它还有稳定的 browser profile，下一次启动可以继续复用登录状态。

因此这是非常适合 C2C 的。

而且 `browser.open` 已支持：

```text
persist: true
```

用于：

> keep tab live across turn settle and idle close



于是 C2C Skill 应该使用：

```js
browser.open({
  name: "c2c-chatgpt",
  url: chatUrl,
  persist: true
})
```

这基本就是 OMP 版的：

```text
markHandoff()
markDeliverable()
```

---

## Browser 默认策略

这里我会明确建议：

```text
OMP-owned headed Chromium
        ↓
DEFAULT

user Chrome relay
        ↓
explicit opt-in only
```

OMP 已经支持将 browser 切换成 visible/headed 模式；现有 `/browser visible` 会把 `browser.headless=false`。

这对 ChatGPT 登录、2FA、CAPTCHA 很重要。

我**不建议默认使用 Browser Relay 接用户自己的 Chrome**。

一方面 C2C upstream 本身非常强调隔离浏览器；另一方面 PR #431 最初提出 external/shared-browser 时，维护侧明确对安全边界提出了保留意见，随后 contributor 将其拆除。

而 OMP-owned shared Chromium 已经同时解决：

```text
登录持久化
+
自动化
+
与用户日常 Chrome 隔离
```

实际上更合适。

# 11. Core 也应该做一个非常小的 executor-neutral 化

不需要重写 Bridge。

当前这部分：

```text
bridge/
mcp/
auth/
pairing/
workspace/
tunnel/
execution/
```

都是可以继续使用的。其安全模型本来就是：

```text
one bridge
=
one workspace
=
one security boundary
```

并且 MCP 是只读。

真正需要修改的主要是两个地方。

第一，Codex sandbox 应从 generic setup/doctor 中抽出来，或者至少增加：

```text
--client codex
--client generic
```

类似的能力。

OMP route 不应该触碰：

```text
~/.codex/config.toml
```

第二，execution record 应 executor-neutral。

这甚至已经有 **PR #412**：

```text
executor?: string

c2c record --executor claude-code
```

并且把：

```text
Codex execution summary
```

改成：

```text
execution summary
```

维护侧的初步 review 认为这个方向是兼容且有价值的。该 PR 截至检查时仍为 open。

OMP 应该写：

```text
executor = "omp"
```

这样 ChatGPT MCP 侧真正不知道也不需要假设执行器是 Codex。

# 12. 因而我会否定四种方案中的三个

| 方案 | 评价 |
|---|---|
| **只复制/改写 SKILL.md** | 可做 PoC；状态机不可靠 |
| **直接把 OMP Adapter 全塞进 codex-with-chatgpt repo** | 可行，类似 PR #431；但造成 upstream/product coupling |
| **重新实现 C2C Bridge** | 完全没有必要 |
| **C2C generic core + OMP Plugin(Extension+Skill)** | **正式实现最合理** |

尤其第三种应该避免，因为 C2C 已经解决了最复杂的部分：

```text
OAuth
pairing
MCP
path containment
sensitive file policy
tunnel
workspace isolation
execution output sanitization
```

这些没有任何必要重新造一遍。

# 13. 我建议最终 repo 结构

我现在更倾向于**不要**上一轮的：

```text
codex-with-chatgpt/
  adapters/
    codex/
    omp/
```

作为最终产品结构。

更干净的是：

```text
codex-with-chatgpt
│
├── bridge/
├── mcp/
├── auth/
├── tunnel/
├── workspace/
└── execution/
        ↑
        │ generic C2C interface
        │
┌───────┴──────────────┐
│                      │
Codex Skill       OMP Plugin
                       │
              ┌────────┴────────┐
              │                 │
        extension.ts        skills/
              │                 │
       state machine       c2c/SKILL.md
       lifecycle gate      browser workflow
       session state
```

而 OMP plugin 自己可以是：

```text
omp-with-chatgpt/
├── package.json
│   └── omp.extensions
│
├── src/
│   ├── extension.ts
│   ├── c2c-client.ts
│   ├── protocol.ts
│   └── state.ts
│
└── skills/
    └── c2c/
        └── SKILL.md
```

OMP 原生支持这种 extension package 同时携带 sibling `skills/` 的结构。

这意味着：

```text
omp plugin install ...
```

一次安装就能获得：

```text
runtime extension
+
skill
```

非常自然。

# 14. 一个我特别建议避免的错误

**不要让 Extension 直接 import OMP Browser internals。**

例如不要：

```ts
import {
  acquireTab,
  runInTab,
} from "@oh-my-pi/pi-coding-agent/tools/browser/tab-supervisor"
```

虽然技术上可能能做到，但会高度耦合 OMP 内部实现。

OMP Browser 官方模型目前是 Eval facade，而 Extension 是另一套稳定 API。

所以保持：

```text
Extension
    ↓ instruct / gate
Agent
    ↓
Skill
    ↓
Browser Eval
```

是更抗版本变化的设计。

# 15. 实施顺序

如果真正准备实现，我会按下面顺序，而不是直接 fork 一大块代码：

1. **先把 C2C generic boundary 做干净**：增加 executor-neutral record；让 OMP 调用 setup/doctor 时不触碰 Codex sandbox；Bridge/Auth/MCP/Tunnel 全部保持原实现。
2. **做一个独立 `omp-with-chatgpt` Plugin**：Extension + bundled Skill，先实现 `/c2c setup|on|off|status`，默认按 session opt-in，而不是一安装就拦截所有 coding task。
3. **把 C2C protocol 状态放进 OMP session**：用 `appendEntry()` 保存 `taskId/iteration/state/waitingFor/chatUrl`，并在 session/branch/tree 恢复；workspace-level connector/project 信息仍由 C2C 管。
4. **实现 deterministic gates**：`before_agent_start` 创建 INIT；`tool_call` 在 GPT PLAN/REVIEW gate 阶段禁止 mutation；`session_stop` 只负责防止未经 review 就宣告完成。
5. **接 OMP Browser Skill**：固定 named persistent tab；OMP-owned visible shared Chromium；DOM-based composer 操作；用户 Chrome relay 只做显式 opt-in fallback。
6. **最后处理并发与恢复**：两个 OMP sessions → 两个 ChatGPT chats；branch → 新 chat + HANDOFF；subagent 不启动独立 C2C 顶层任务；断开/重启后从 OMP transcript 恢复。
7. **最后才考虑 upstream**：generic core patch 很适合给 `codex-with-chatgpt` 提 PR；OMP adapter 本身可以独立仓库，不必等待上游接受 multi-executor 的产品方向。

## 最终判断

所以，对上一轮方案我会做这样一个修订：

```text
上一版
────────────────────────────
C2C Bridge unchanged
        +
OMP Harness Adapter / Skill

             ↓

二次分析后的方案
────────────────────────────
Executor-neutral C2C Core
        +
OMP-native Plugin
    ├── Extension
    │    ├── lifecycle
    │    ├── protocol FSM
    │    ├── gates
    │    └── session state
    │
    └── Skill
         └── ChatGPT browser workflow
```

**这是我目前认为最稳健的实现方法。**

它同时利用了两个项目各自最成熟的部分：

```text
codex-with-chatgpt
    → MCP / OAuth / Tunnel / Workspace security

OMP
    → Session / Extension / Hook / Browser / Agent execution
```

而不是强行让其中任何一个项目承担它本来不擅长的职责。

还有两个细节我会在实际 spec 中明确列为 **P0 correctness requirement**：**subagent 不得自行创建新的 C2C 顶层 task**，以及 **Git worktree 的 MCP root 必须与实际被 review 的 checkout 一致**。这两个问题在简单 demo 中很容易被忽略，但对于你当前这种 OMP 多 agent / 长流程使用方式，会直接决定这个插件是否真的可靠。
